# 修正内容：ログ収集を一時停止すると「本日 ○/50回」が 0 に戻る

- ブランチ：`fix/usage-count-reset-on-pause`
- 状態：**原因特定・修正済み**（原因は 9 章、修正内容は 10 章）

## 1. 症状

チャット画面上部の利用回数表示（例：`ID: P001 本日 0/50回`）が、「収集を一時停止」→「収集を再開」の操作をすると 0 に戻る。

- 時刻に関係なく起きる（研究者の報告）
- 該当箇所：[chat.js の chatBar()](../02_scripts/extension/media/chat.js) の `本日 ${u.requestsToday}/${u.requestsPerDay}回`

## 2. 困ること

1日の利用枠（参加者ごとに 50 回）は、一時停止・再開の操作に関係なく、その日の合計で数える必要がある。
一時停止→再開で回数が 0 に戻ると、

- 参加者に表示される残り回数と、実際に使える回数が食い違う
- 一時停止・再開をきっかけに、1日の利用枠が意図どおりに制限されなくなる（または意図しないタイミングで制限される）

## 3. 期待する動作

- 「本日 ○/50回」は、一時停止・再開をしても**その日の利用回数を保ったまま**表示する
- 0 に戻るのは、1日の区切り（後述）をまたいだときだけ
- 一時停止中は送信できないので、回数は増えない（今の仕様どおり）

## 4. 今のコードの仕組み（調査結果）

| 項目 | 内容 | 場所 |
|---|---|---|
| 回数を数える場所 | サーバー側。`/chat` を受けるたびに Firestore の `usage/user_<研究用ID>_<日付>` を +1 する | [api.ts](../02_scripts/server/src/api.ts) `usageKeys`・`/chat` |
| 表示する値 | 拡張が `/status` を呼び、返ってきた `usage.requestsToday` を表示する | [api.ts](../02_scripts/server/src/api.ts) `statusBody`、[extension.ts](../02_scripts/extension/src/extension.ts) `refresh()`・`postState()` |
| 一時停止の処理 | 拡張の端末内フラグ（`researchLlm.collectionPaused`）を切り替え、`refresh()` で画面を描き直すだけ。サーバーの回数には触れていない | [extension.ts](../02_scripts/extension/src/extension.ts) `case "setPaused"`、[eventLogger.ts](../02_scripts/extension/src/eventLogger.ts) `setPaused()` |
| 1日の区切り | `USAGE_TIME_ZONE`（既定 `America/Los_Angeles`）の 0 時。日本時間では冬 17 時・夏 16 時 | [config.ts](../02_scripts/server/src/config.ts) |
| 保存先 | 本番は Firestore（`STORE: firestore`）。ローカル起動はメモリ DB | [deploy.sh](../02_scripts/deploy/deploy.sh)、[index.ts](../02_scripts/server/src/index.ts) |

**コードを読んだ範囲では、一時停止・再開で回数を 0 にする処理は見つからなかった。**
そのため、下の候補を順に確かめて原因を特定する必要がある。

## 5. 原因の候補

| # | 候補 | 当てはまる場合の見え方 | 可能性 |
|---|---|---|---|
| A | 拡張の表示だけが 0 になっている（サーバーの回数は正しい） | 管理画面の「本日の利用」は正しい回数のまま | 要確認 |
| B | サーバーの回数そのものが 0 になっている | 管理画面の「本日の利用」も 0 | 要確認 |
| C | 1日の区切り（日本時間 16〜17 時）をまたいだ | その時刻の前後だけで起きる | 低い（時刻に関係なく起きるとの報告） |
| D | ローカル起動のサーバー（メモリ DB）を再起動した | ローカル環境で試したときだけ起きる | 本番で起きるなら該当しない |

## 6. 原因を特定する手順

1. 本番サーバーにテスト用参加者でつなぎ、チャットを 2〜3 回送る。画面の「本日 ○/50回」が増えることを確認する
2. 管理画面の参加者一覧で、その参加者の「本日の利用」の回数を控える
3. 拡張で「収集を一時停止」→「収集を再開」を押す
4. 拡張の表示と管理画面の「本日の利用」を見比べる
   - 拡張だけ 0 → 候補 A（拡張側の表示処理を調べる）
   - 両方 0 → 候補 B（サーバー側・Firestore の保存を調べる）
   - 両方とも正しい回数のまま → 再現条件が別にある（操作した時刻・拡張のバージョン・VS Code の再起動有無などを記録する）
5. 再開後にもう 1 回送信し、表示が「控えた回数 + 1」になるかを確認する

## 7. 修正方針（原因に応じて決める）

| 原因 | 修正方針 |
|---|---|
| A | 一時停止・再開時に送る画面状態（`state`）に、必ずサーバーから取得した最新の `usage` を入れる。取得に失敗した場合は前回の値を保つ（0 や空で上書きしない） |
| B | 利用回数のキー（研究用ID・日付）が一時停止・再開の前後で変わっていないか、Firestore の保存処理（`addUsage`／`getUsage`）を調べて直す |
| C | 1日の区切りを日本時間 0 時に変えるかを研究者が判断する（Gemini API の日次上限のリセット時刻とずれる点に注意） |
| D | 不具合ではない（運用手順書に「ローカル起動では再起動で回数が消える」と注記する） |

## 8. 修正後の確認

- 拡張のテストに「一時停止・再開の前後で `usage` の表示値が変わらない」ことを確かめるテストを追加する
- サーバーのテスト（[api.test.ts](../02_scripts/server/test/api.test.ts)）で、送信後の `/status` の回数が保たれることを確認する
- 6 章の手順を本番環境のテスト用参加者で再度行い、0 に戻らないことを確認する
- `02_scripts/server/` と `02_scripts/extension/` で `npm run lint` と `npm test` が通ること

## 9. 調査結果（2026-11-09）

本番環境（Cloud Run `research-llm`）の設定とリクエスト記録（パスと応答コードのみ）を確認した。

| 確認したこと | 結果 |
|---|---|
| 保存先 | `STORE=firestore`。サーバーの再起動で回数が消えることはない（候補 D は本番では該当しない） |
| 1日の区切り | `USAGE_TIME_ZONE` は未設定のため既定の `America/Los_Angeles`。2026-11-01 に米国の夏時間が終わったので、今は日本時間 17 時に切り替わる |
| 最後に `/chat`（エージェントへの依頼）が届いた日時 | 2026-11-02 日本時間 12:20〜16:28。**それ以降は 1 件も届いていない** |
| 11-04・11-06 | `/events`（ログ送信）のみ。一時停止・再開などのイベント送信と考えられる |
| 11-09 | `/status`（状態確認）のみ |

### わかったこと

- 「本日 ○/50回」は**その日に送った依頼の回数**なので、11-02 に使った回数は翌日以降の表示に含まれない
- 11-02 の 16:28 以降は依頼が送られていないため、11-04・11-06・11-09 の表示が 0 になるのは仕様どおり
- 一時停止・再開がきっかけで 0 になったのではなく、**依頼を送った日と表示を見た日が違っていた**可能性が高い

### 現象が起きた 2026-11-02 の記録（日本時間）

| 時刻 | 記録 |
|---|---|
| 16:26〜16:28 | `/chat`（依頼）が 7 回届く。これがこの日最後の依頼 |
| 17:00 | 太平洋時間の 0 時。サーバーの「本日」の日付がここで切り替わり、回数が 0 から数え直しになる |
| 17:01:40・17:01:44 | `/status`（状態確認）が 2 回 |
| 17:01:52 | `/events`（ログ送信）が 2 回 |

17:01 の「状態確認 → ログ送信」は、一時停止・再開を押したときの動き（`setPaused` → `refresh()`、停止・再開イベントの送信）と一致する。
**一時停止を押したのが日付の切り替わり（17:00）の直後だったため、回数が 0 に戻ったように見えた**と考えられる（5 章の候補 C）。

### 次に確かめること

同じ日のうちに次の操作をして、回数が保たれるかを確認する。

1. チャットを 1 回送る（表示が 1 以上になる）
2. 「収集を一時停止」→「収集を再開」を押す
3. 表示が 1 の手順の回数のままなら、不具合ではない（5 章の候補 C）

1 回の依頼でもエージェントがツールを使うたびにサーバーへ問い合わせるため、1 回の依頼で回数が 2 以上増えることがある点にも注意する。

## 10. 決定した修正（2026-11-09）

原因は不具合ではなく、1日の区切り（日本時間 17 時、夏は 16 時）を参加者が画面上で知る手段がなかったこと。
区切りは Gemini 無料枠のリセット時刻に合わせた設計（教授提出資料・README・運用手順書に記載済み）なので**変えず**、**リセット時刻を画面に表示する**ことにした（研究者が判断）。

| 変更 | 内容 | 場所 |
|---|---|---|
| サーバー | `/status` の `usage` に `resetsAt`（次に回数が 0 に戻る時刻、ISO 形式）を追加。夏時間の切り替わりにも対応 | [util.ts](../02_scripts/server/src/util.ts) `nextDayStart()`、[api.ts](../02_scripts/server/src/api.ts) `statusBody` |
| 拡張 | 表示を「本日 3/50回（17:00にリセット）」に変更。時刻は参加者の端末の時刻で表示。`resetsAt` を返さない古いサーバーでは従来どおりの表示 | [chat.js](../02_scripts/extension/media/chat.js) `chatBar()`、[apiClient.ts](../02_scripts/extension/src/apiClient.ts) |
| テスト | リセット時刻の計算（冬時間・夏時間・切り替え日・日本時間）と、`/status` が `resetsAt` を返すことを確認 | [util.test.ts](../02_scripts/server/test/util.test.ts)、[api.test.ts](../02_scripts/server/test/api.test.ts) |
| 手順書 | 参加者向け手順書に、表示の見方と「一時停止・再開では回数は変わらない」ことを追記 | [参加者向け手順書.md](参加者向け手順書.md) |

### 反映に必要な作業

- サーバーの再デプロイ（`02_scripts/deploy/deploy.sh`）
- 拡張の `.vsix` の作り直しと配布 ZIP の作り直し（`02_scripts/deploy/build-distribution.sh`）。古い拡張のままでも動作に問題はなく、リセット時刻が表示されないだけ
- サーバーだけ先に更新しても、古い拡張は追加された項目を無視するので影響はない
