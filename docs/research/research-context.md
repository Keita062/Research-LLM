## 1. このリポジトリの位置づけの変化

| 版 | 内容 | 状態 |
|---|---|---|
| v1（タグ `v1-chatbot`） | 研究室用LLMチャットボット。Gemini APIとのチャット入出力をDBに保存し、管理画面で利用統計を見る | 完成済み。ただし研究方針の変更により、研究データの収集手段としては使わない |
| v2（これから） | 研究室メンバーが **普段の開発（VS Code／Unity）で使うAIコーディングエージェント** の利用イベントを、本人の同意のもとで自動収集する基盤 | 要件定義から着手 |

### 方針変更の理由（2026-09-28）

- 研究室のメンバーは開発相談を既存のCoding Agent上で行うため、研究用チャットボットを配っても自然なデータが集まらない
- そこで、通常の開発作業の中で発生するCoding Agentの利用イベントを Hook 等から観測する方式に転換した
- 研究室内でClaude Code／Codex等の有料契約者は少なく、無料でも使っている人が少ない。
  そのため「研究室共通のAI開発環境を整備し、使ってもらいながらデータを集める」ことを副次目的とする

### v1から流用できそうな資産（要件定義で要検証）

- 認証・アカウント管理（メール確認・パスワード管理・RBAC・セッション）
- 管理ダッシュボードの枠組み（Recharts・集計クエリ）
- PostgreSQL＋Prisma のDB基盤、レート制限の仕組み
- Gemini チャット機能・添付ファイル機能は v2 の研究目的には直接不要な可能性が高い（削除するかどうかはユーザー承認事項）

## 2. 想定している全体構成（作業仮説。要件定義・設計で見直してよい）

```
参加者のPC（Windows/macOS、VS Code・Unity）
  └ Coding Agent ──Hook等──▶ Collector（最小化・仮名化）
                                └▶ ローカルバッファ（SQLite等）
                                     └─(ネット接続時に自動同期・再送・重複排除)─▶ 研究用API ─▶ 研究用DB
研究者
  └ 管理画面（収集の正常性・欠損の監視） ／ SQLで抽出 → Pythonで分析
```

- 被験者のログ提出作業はゼロにする（初回の同意・インストール・研究用ID設定以降は自動）
- 設定・収集停止・アンインストールを参加者自身が簡単に行えること

## 3. 分析の単位（暫定）

| 用語 | 定義 |
|---|---|
| ターン | 「人の入力 → AIの出力 → 人の反応」の1往復 |
| エピソード | 1つの依頼に関するターンの連鎖。承認／放棄／未解決 のいずれかで終端する（暫定分類） |
| エピソード境界 | 暫定ルールとして時間ギャップ方式（例：15〜30分無操作で終了）を採用。妥当性は実装段階で検証する |

RQ1〜RQ7 と分析方法の過去案は [rq-analysis-draft-v1.md](rq-analysis-draft-v1.md) を参照（RQ番号は確定版と異なる旧体系）。

## 4. データ収集の方針（教授への相談資料 2026-09-28 時点の内容。変更には教授・倫理手続の確認が必要）

| 取得候補 | 研究上の用途 | 初期方針 |
|---|---|---|
| 研究用ID、時刻、セッション識別子 | 個人内の週ごとの変化、利用頻度 | 取得する |
| イベント種別、ツール名、所要時間、成否 | 依頼と作業の流れ、ツール利用の変化 | 取得する。ただしコマンド引数と出力本文は除外 |
| プロンプト・回答の本文 | 依頼内容と修正指示の質的分析 | **初期試行では中央に送信しない**。必要性と追加同意を別途検討 |
| コード、ファイル名、絶対パス、認証情報 | 現時点の研究目的には必須でない | **収集・送信しない** |

- イベントから承認・拒否やセッション終了を確実に観測できるかは製品ごとに異なる。**取得可能と実証できた項目だけ**を測定項目にする
- 匿名化ではなく **仮名化** として扱う。氏名と研究用IDの対応表は研究ログとは別に保管し、アクセス権を限定する
- 研究参加は任意。不参加・途中撤回で不利益を生じさせない。「環境の利用」と「研究へのログ提供」は分けて説明する
- 教授・研究者が個々の利用内容を日常の評価や監督に使わない。報告は原則として集計値
- 私用作業や第三者の情報を含む作業では、参加者が収集を止められるようにする

### 既知の論点（要件定義で必ず扱う）

- 確定版RQ（RQ1〜RQ3）は「人間とAIの行動の種類と連鎖」を扱う。人間の行動（承認・修正指示・追加質問・放棄など）を
  **本文を中央に送らずに** どこまで分類できるかが最大の論点。
  例：Hookのイベント種別・タイミングだけで判定する／ローカルで分類しラベルのみ送信する／追加同意を得て本文を扱う 等
- RQ4〜RQ7 の「成果物の作成過程の変化」を、コード・ファイル名を収集せずにどう捉えるか（例：変更行数などの集計値のみ）

## 5. 製品選定の制約

- 候補は、参加者が **各自正規に・無償または低コストで** 利用できるAIコーディングエージェントとする
- 共有アカウントや個人向け無料枠の研究室内での使い回しを前提にしない
- **Gemini CLI の個人無料枠は前提にできない**：Googleの公式案内により 2026-06-18 以降、個人向け Gemini Code Assist 等による Gemini CLI の利用は停止
  - https://developers.google.com/gemini-code-assist/docs/deprecations
  - https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/
- 比較観点：利用資格・料金・上限、入力データの取扱い（規約）、Hook等のログ取得機能、OS（Windows含む）・VS Code・Unity との相性

## 6. 研究の進め方と現在地

1. 準備：研究計画・収集項目・保存/削除手順の確定、候補製品の料金・規約・ログ取得機能の検証 ← **いまここ（開発は要件定義から）**
2. 小規模試行：希望者2〜3名。ログ欠損・機微情報の混入・負荷・費用を確認
3. 本実施：教授の承認後に募集。期間は4〜8週間を仮置き
4. 分析：収集停止後、SQLで抽出しPythonで参加者別・週別の変化を分析
