# Playbook 01：v2 要件定義（チャット型 → エージェント利用ログ収集基盤）

- マクロ：`!rllm-req`
- 使う場面：Research-LLM v2 の要件定義書を作る／改訂するとき
- 前提資料（必ず最初に読む）：`AGENTS.md`、`docs/research/research-questions.md`（RQ正本）、`docs/research/research-context.md`、`docs/research/rq-analysis-draft-v1.md`、`docs/requirements.md`（v1要件）

## Overview

このリポジトリは、研究室用LLMチャットボット（v1、タグ `v1-chatbot`）を、
**研究室メンバーが普段の開発（VS Code／Unity）で使うAIコーディングエージェントの利用イベントを、本人の同意のもとで自動収集する基盤（v2）** に切り替える。
このPlaybookのゴールは、卒業研究のRQ1〜RQ7に答えるために必要十分な v2 の要件定義書を作り、ユーザー（研究者本人）の承認を得ることである。

成果物：
1. `docs/v2/requirements.md`（要件定義書）
2. `docs/v2/rq-traceability.md`（RQ → 必要な観測データ → 取得手段 → 要件ID の対応表）
3. `docs/v2/agent-survey.md`（候補Coding Agentのログ取得能力の調査結果。出典URLと確認日つき）
4. 上記を含むPull Request（ドラフトで作成し、ユーザーのレビューを受ける）

**このPlaybookではアプリケーションコードを変更しない。** ドキュメントのみを扱う。

## What's Needed From User

- 研究者本人の頭の中にある構想（Procedure 5 のヒアリングで回答してもらう）
- 教授の合意状況、倫理審査・情報管理手続の進捗
- 参加者の想定環境（人数、OS、VS Code／Unityの比率、普段使っているAIツール）
- 研究用サーバーの置き場所の方針（研究室サーバー／クラウド）と費用の上限
- 要件定義書ドラフトへのレビューと承認

## Procedure

1. 前提資料を読み、研究目的・達成条件・RQ1〜RQ7・データ収集方針・製品選定の制約を把握する。読み終えたら、理解した内容を5〜10行の箇条書きでチャットに報告する。
2. v1 のコードを棚卸しする（`prisma/schema.prisma`、`src/actions/`、`src/lib/`、`src/app/`）。機能ごとに「v2で流用／改修して流用／不要候補」を判定し、理由とともに表にまとめる。
   - 不要候補を **削除するかどうかはユーザー承認事項**。この段階では判定のみ行う。
3. RQトレーサビリティ表（`docs/v2/rq-traceability.md`）を作る。RQ1〜RQ7 それぞれについて以下を列にする：
   - 答えるために必要な観測データ（例：イベント種別、時刻、ツール名、成否、承認/拒否、ターン位置）
   - そのデータが **本文（プロンプト・回答・コード）を中央に送らずに** 得られるか（可／条件付き／不可）
   - 条件付き・不可の場合の代替案（例：ローカルで分類しラベルのみ送信、集計値のみ送信、追加同意）
   - 対応する要件ID（Procedure 6 で採番後に埋める）
4. 候補Coding Agentのログ取得能力を調査し `docs/v2/agent-survey.md` にまとめる。
   - 候補の例：Claude Code、OpenAI Codex（CLI／IDE拡張）、GitHub Copilot（VS Code のエージェントモード）、Gemini CLI の後継（Antigravity CLI 等）、Cline など。候補の追加・除外は理由を書けばよい
   - 比較観点：利用資格・料金・無償枠の有無、Hook/イベント通知の仕組み（どのイベントが取れるか：依頼送信、ツール実行前後、承認/拒否、応答完了、セッション開始/終了）、Hookに渡るペイロードの項目、Windows対応、VS Code／Unity との相性、規約上のデータ取扱い
   - **根拠は公式ドキュメントに限る**。各項目に出典URLと確認日を書く。確認できなかった項目は「未確認」と書き、推測で埋めない
5. ユーザーにヒアリングする。Procedure 1〜4 で分かった論点をもとに、**質問を1回あたり10個以内にまとめて** チャットで聞き、回答を待つ。少なくとも次の論点を含める：
   - 研究者本人が考えている構想・やりたいこと（自由記述）
   - 対象にするCoding Agent（1製品に絞るか、複数対応か）
   - 人間の行動（承認・修正指示・追加質問・放棄など）の分類を、本文を送らずにどう行うか（research-context.md §4「既知の論点」）
   - 参加者の人数・OS・期間、研究用サーバーの置き場所と費用上限
   - v1 の不要候補機能（Geminiチャット・添付ファイル等）を残すか削除するか
   回答が足りない論点は「未決事項」として扱い、勝手に決めない。
6. 要件定義書 `docs/v2/requirements.md` を作成する。章立ては Specifications に従う。要件には ID を振る（機能要件 `FR-xx`、非機能要件 `NFR-xx`、データ要件 `DR-xx`、プライバシー・倫理要件 `PR-xx`）。採番後、トレーサビリティ表の要件ID列を埋める。
7. 自己レビューする。Specifications のチェックリストを1つずつ確認し、満たしていない項目を直す。
8. ブランチ `devin/req-v2-<YYYYMMDD>` を作り、成果物をコミットして **ドラフトPR** を作成する。PR本文には、ヒアリングで決まったこと・未決事項・ユーザーに判断してほしい点を箇条書きで書く。
9. ユーザーのレビューコメントに対応する。承認されたら PR を Ready for review に変更し、要件定義が完了したことと、次は `!rllm-design` で設計に進めることをチャットで伝える。マージはユーザーが行う。

## Specifications

`docs/v2/requirements.md` は次の章立てを持つこと：

1. 目的・背景（研究目的と、v1からの方針転換の理由）
2. 用語定義（ターン、エピソード、エピソード境界、研究用ID、仮名化 など）
3. 対象範囲（対象とするCoding Agent・OS・期間・人数。対象外も明記）
4. 全体構成（Collector／ローカルバッファ／同期／研究用API／DB／管理画面／分析用エクスポート）
5. 機能要件（FR）：参加者側（導入・同意・研究用ID設定・収集の一時停止・アンインストール・データ削除申請）と研究者側（収集状況の監視・欠損検知・エクスポート）の両方
6. データ要件（DR）：収集するイベントと項目の一覧表。各項目に「中央に送信／ローカルのみ／収集しない」と、その項目が必要なRQを書く
7. プライバシー・倫理要件（PR）：同意・撤回・仮名化・対応表の分離・アクセス制限・保存期間・削除・誤収集時の対応
8. 非機能要件（NFR）：オフライン時のバッファ、再送と重複排除、参加者PCへの負荷、Windows対応、セキュリティ（通信の暗号化、認証）、運用費用
9. v1 資産の扱い（流用／改修／不要候補の表と、ユーザーの判断結果）
10. 未決事項（誰が・いつまでに決めるか）
11. 参考資料（出典URL）

チェックリスト：
- [ ] RQ1〜RQ7 のすべてが、少なくとも1つの要件（FR/DR）に対応づいている
- [ ] すべての DR 項目に、必要とするRQが書かれている（RQに使わない項目は収集しない）
- [ ] プロンプト・回答本文、コード、ファイル名、絶対パス、認証情報が、既定設定で中央に送信される要件になっていない（変える場合は「教授・倫理手続の承認が前提」と明記）
- [ ] 製品仕様に関する記述にはすべて出典URLと確認日がある
- [ ] ユーザーが回答していない論点を、決定事項として書いていない
- [ ] `docs/requirements.md`（v1）と `src/` 以下のコードは変更していない

## Advice and Pointers

- これは「観測」のための基盤であり、参加者の開発作業を妨げてはいけない。Collector の失敗が Coding Agent の動作を止める設計（Hookがエラーで終了してエージェントをブロックする等）は避ける。
- 参加者はUnity開発者が多く、**Windows が主な実行環境になる可能性が高い**。Devin の作業環境は Linux なので、OS依存の前提（bashのみのスクリプト、POSIXパス）を要件に紛れ込ませない。
- 同期は「イベントIDをクライアント側で採番（UUID等）→サーバー側で一意制約により重複排除」の形が扱いやすい。時刻はUTCで保存し、参加者のタイムゾーンは別項目にする。
- エピソード境界は時間ギャップ方式が暫定ルール。閾値を後から変えて再計算できるよう、**エピソードは生ログから派生させる**（収集時に確定させない）方針を推奨する。
- 「仮名化」と「匿名化」を混同しない。研究用IDと氏名の対応表は再識別可能な情報であり、研究ログDBとは分けて保管する。
- 教授向け資料の通り、結果は「導入された環境での変化」として解釈する。要件定義書の目的欄で因果効果を主張しない。
- v1 の要件定義書（`docs/requirements.md`）の章立て・書き方は参考にしてよい。
- ドキュメント・PR・チャットはすべて日本語で書く。

## Forbidden Actions

- 実データの収集開始、参加者への配布、本番環境へのデプロイ（教授の合意と倫理手続が終わるまで禁止）
- `src/`・`prisma/` などアプリケーションコードの変更、v1 機能の削除（このPlaybookはドキュメントのみ）
- `main` ブランチへの直接 push、force push、自分の PR のマージ
- リポジトリの公開設定・権限設定の変更
- `.env` や APIキー・パスワード等の秘密情報のコミット
- 共有アカウントや個人向け無料枠の使い回しを前提にした製品選定
- 出典のない製品仕様の記載、ユーザー未回答の論点を推測で決定事項にすること
